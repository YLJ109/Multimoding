## 1. 路线图目标

项目已经拥有可运行的 PyQt6 训练应用，也已经形成了多轮升级方案。当前最大的风险不是缺少功能想法，而是多个模块同时争抢：

- 摄像头。
- YOLO。
- 姿态时间戳。
- 角色骨架。
- 动作播放权。
- 显存。
- 主线程。
- 皮肤材质槽。
- 语音和模仿的控制权。

路线图的核心任务是：

1. 先建立共享数据层和角色运行时。
2. 再建立实时模仿和语音控制。
3. 然后接入角色、皮肤、评价和游戏化。
4. 最后进行 6GB 显存、隐私、许可证和比赛发布硬化。
5. 每个阶段有明确进入条件和退出条件。
6. 不跨越依赖顺序提前实现高风险 UI。

## 2. 不可违反的实施原则

### 2.1 数据优先于界面

先确定：

- `PoseFramePacket`
- `MotionIntent`
- `ActorPoseFrame`
- `QualitySnapshot`
- `SkinManifest`
- `RuntimeMetrics`

再实现页面。界面不能先依赖没有稳定的数据结构。

### 2.2 单生产者原则

- 一个主摄像头只有一个采集者。
- 一个主动作模型只有一个主推理结果。
- 一个角色只有一个最终姿态写入者。
- 一个皮肤槽只有一个事务提交者。
- 一个 SQLite 文件避免多线程同时写。

### 2.3 回退优先于炫技

所有核心功能必须能在低质量模式下工作：

- 无手部模型时仍能全身模仿。
- 无人脸时仍能头部跟随。
- 无完整皮肤时仍能单色显示。
- 无云端时仍能本地控制。
- 无 WebEngine 时仍能原生骨架预览。
- 无网络时仍能播放本地资源。

### 2.4 先测量再优化

每个里程碑必须采集：

- 平均延迟。
- P95 延迟。
- 平均 FPS。
- 最大连续丢帧。
- VRAM 峰值。
- CPU 和 RAM。
- 皮肤切换时间。
- 30 分钟稳定性。

没有测量数据，不进入下一阶段。

### 2.5 一个阶段只解决一类主要风险

不把“角色导入、皮肤热切换、语音识别、LLM 规划、实时模仿”同时塞进一个不可回退的大提交。

### 2.6 最终人物表示硬约束

- 跟舞训练页的大画面只显示视频动作包驱动的 3D 标准机器人。
- 跟舞训练页不创建用户 3D 角色、不做用户 3D 重建、不显示用户 3D 网格。
- 跟舞训练页的摄像头位于左上角，只显示用户二维骨架和评分颜色。
- 机器人指挥中心的大画面只显示 3D 机器人，左上角摄像头仍然只显示用户二维骨架。
- 机器人指挥中心的用户姿态通过重定向驱动机器人，而不是把用户变成 3D 人物。
- 机器人三维骨架和用户二维骨架始终显示，只能调整细节和透明度，不能完全关闭。
- 同一时刻只允许一个工作区占用摄像头、YOLO 和主 WebGL 场景。
- 本条硬约束以 `docs/ULTIMATE_3D_INTERACTION_PLAN_V9.md` 为最终解释。

## 4. 里程碑总览

| 阶段 | 名称 | 主要目标 | 预计 |
|---|---|---|---:|
| M0 | 契约冻结 | 统一数据模型、模块边界、验收标准 | 1 至 2 天 |

## 5. M0：契约冻结

### 5.1 目标

在编码前冻结 V8 所需的核心契约。

### 5.2 交付物

- `PoseFramePacket` 字段和版本策略。
- `MotionIntent` 枚举和参数范围。
- `ActorPoseFrame` 字段。
- `QualitySnapshot` 字段。
- `SkinManifest` Schema。
- `RuntimeMetrics` 字段。
- 模块职责表。
- 线程所有权表。
- 错误码和降级原因表。
- 数据落盘和隐私边界。
- 资源许可证记录格式。

### 5.3 进入条件

- V8 文档评审通过。
- 用户确认机器人指挥中心为主舞台。
- 用户确认云端服务可配置。
- 用户确认媒体资源本地保存。
- 用户确认比赛使用。

### 5.4 退出条件

- 所有关键数据有唯一负责人。
- 每个字段有类型、单位和版本。
- 不允许出现多个模块各自定义同名但不同含义的数据。
- JSON Schema 能校验样例。
- 线程边界和 UI 边界写明。
- 后续阶段不得无版本地修改契约。

### 5.5 风险

- 过早定义过度复杂的字段，导致实现负担。
- 字段名与现有项目语义冲突。
- 只为机器人设计，忽略训练页复用。

## 6. M1：运行时基础

### 6.1 目标

建立角色、舞台、动作层和资源治理的基础，不接语音和复杂模仿。

### 6.2 交付物

- `ActorRuntime` 单写入者。
- `StageRuntime` 场景和相机所有权。
- `AnimationGraph` 待机、走、跑、跳基础状态。
- `MotionStack` 动作层。
- `SkinBinding` 空实现和槽约定。
- `ResourceGovernor` 指标采集。
- `RenderBridge` Python 到 WebEngine 的受限命令桥。
- 当前训练页的兼容适配层。
- 原生骨架回退。

### 6.3 进入条件

- M0 契约冻结。
- 现有训练页和验证脚本仍能运行。
- Three.js 本地资源已验证。

### 6.4 退出条件

- 单个角色可以由一个运行时稳定驱动。
- 待机、走、跑、跳状态可以单独验证。
- 关闭 WebEngine 后原生回退可用。
- 关闭窗口后无活跃渲染循环。
- 姿态不会被多个模块直接写骨骼。
- 资源治理器能显示 CPU、RAM、VRAM 和 FPS 快照。

### 6.5 不允许事项

- 不接云端 LLM。
- 不实现复杂皮肤。
- 不重写现有训练评分。
- 不在主线程做模型推理。

## 7. M2：动作包与资产基线

### 7.1 目标

把现有 `*.dmotion.json` 和视频转 3D 结果升级为可管理的动作资产。

### 7.2 交付物

- `.dmotion` ZIP 包格式。
- `manifest.json`。
- `poses.npz`。
- `quality.npz`。
- `retarget.json`。
- 封面图。
- 音乐和节拍信息。
- 许可证信息。
- 校验和。
- 旧 `*.dmotion.json` 兼容读取。
- 舞蹈包卡片数据模型。
- 解析状态和质量报告。

### 7.3 进入条件

- M1 可以稳定播放入门动作。
- 现有参考视频解析链路可用。
- 动作时间轴和音乐时钟策略已确定。

### 7.4 退出条件

- 动作包可以导入、校验、缩略图显示、重命名和删除。
- 动作包损坏时不会导致界面崩溃。
- 旧包可以迁移或只读打开。
- 动作包不含原始用户视频。
- 音乐、封面和许可证缺失时有明确状态。

### 7.5 可并行项

- 舞蹈包卡片 UI 可以在数据模型稳定后并行开发。
- 视频转 3D 后端插件可以先做接口，不要求第二阶段就接入多个模型。

## 8. M3：角色与皮肤基础

### 8.1 目标

建立可复用 Humanoid 角色和基础皮肤槽。

### 8.2 交付物

- 统一 Humanoid 骨骼契约。
- GLB 角色加载。
- VRM 可选适配接口。
- 角色能力声明。
- 角色 LOD。
- 默认机器人角色。
- 基础真人比例角色。
- 颜色皮肤。
- PBR 基础皮肤。
- 皮肤清单和许可证。
- 皮肤缓存 LRU。
- 材质槽替换事务。

### 8.3 进入条件

- M1 的 `ActorRuntime` 和 `SkinBinding` 稳定。
- 默认角色资源许可证完成确认。
- 角色坐标系和米制单位统一。

### 8.4 退出条件

- 至少两个角色可以在同一动作契约下播放同一动作。
- 至少三套皮肤可以切换。
- 切换皮肤不重建骨架。
- 切换皮肤不重置动作。
- 失败可以回退旧皮肤。
- 连续切换 20 次后显存不持续增长。
- 用户导入资产不会自动上传。

### 8.5 风险

- 不同角色的骨骼命名和初始姿态不同。
- VRM 材质和 GLB 材质标准不同。
- IP 模型的许可证边界不清。
- 高面数模型不适合 6GB 显存。

## 9. M4：Pose 总线和模仿核心

### 9.1 目标

建立本项目的核心技术资产：共享姿态总线和实时全身模仿。

### 9.2 交付物

- `PoseFrameBus`。
- 单摄像头采集。
- 单主动作推理。
- 主人物跟踪。
- 缺口修复。
- 标准化。
- 人体校准。
- 自适应平滑。
- Humanoid 重定向。
- 根节点可选控制。
- 模仿状态机。
- 模仿范围骨骼掩码。
- 基础质量面板。
- 摄像头丢失安全保持。
- 原生骨架回退。

### 9.3 进入条件

- M1 单写入者稳定。
- M3 Humanoid 契约稳定。
- 现有 YOLO 推理已通过 GPU/CPU 输出转换测试。
- 训练页不会与指挥中心重复推理。

### 9.4 退出条件

- 机器人可以实时模仿用户全身。
- 开始、暂停、停止、恢复稳定。
- 切换上半身和全身不重置姿态。
- 低置信度不会导致乱跳。
- 短时遮挡可以预测并恢复。
- 长时丢失进入安全保持。
- 姿态延迟达到目标范围。
- 不重复运行 YOLO。
- 连续运行 10 分钟无显存增长。

### 9.5 关键验收动作

- 站立。
- 双手上举。
- 单手挥手。
- 拍手。
- 下蹲。
- 提膝。
- 转身。
- 原地跑。
- 跳跃。
- 一侧遮挡。
- 第二个人进入画面。
- 摄像头拔掉再恢复。

## 10. M5：手部、人脸与质量

### 10.1 目标

加入低帧率、局部 ROI 的 Hands 和 Face，不抢占核心全身姿态。

### 10.2 交付物

- MediaPipe Hands 适配器。
- MediaPipe Face 适配器。
- 手势本地规则。
- OK 手势识别。
- 手掌打开、握拳、比心、指向、挥手。
- 客观人脸特征。
- 无手指角色替代反馈。
- 无面部角色灯光反馈。
- 隐私开关。
- 质量融合。
- 手部和人脸降级。

### 10.3 进入条件

- M4 全身模仿稳定。
- 手腕 ROI 可用。
- 摄像头帧不会在每个模块重复深拷贝。
- 目标角色的手部和面部能力已声明。

### 10.4 退出条件

- 手部模型开启后全身 FPS 仍达标。
- 关闭 Face 后完全停止人脸处理。
- 无手指角色有可理解的替代反馈。
- 手部低帧率不会造成全身动作抖动。
- 人脸模块默认关闭或明确告知。
- 原始人脸帧和关键点不持久化。

## 11. M6：机器人指挥中心与语音基础

### 11.1 目标

建立机器人指挥中心页面、语音链路、动作队列和实时字幕。

### 11.2 交付物

- 机器人指挥中心独立页面。
- 麦克风状态。
- VAD。
- ASR 适配器。
- 临时字幕和最终字幕。
- 本地安全快速通道。
- 本地确定性命令。
- 动作白名单。
- 动作队列。
- 防冲突校验。
- 场景和镜头基础命令。
- TTS 回复。
- 云端配置入口。
- 语音日志隐私策略。

### 11.3 进入条件

- M4 和 M5 数据稳定。
- M1 的 ActorRuntime 可以执行动作意图。
- M2 的舞蹈包可以播放和暂停。
- 安全命令不依赖网络。

### 11.4 退出条件

- 用户可以说“开始模仿”“停止模仿”“上半身”“换皮肤”“暂停舞蹈”。
- 字幕显示临时和最终识别结果。
- 安全命令延迟小于 150 毫秒。
- 网络断开时本地命令仍工作。
- 未知命令不会被执行。
- 动作队列不会无限增长。
- 第二个人物不会触发语音误操作。

### 11.5 云端通道

只有在本地命令稳定后才接入 LLM 复杂规划。LLM 失败必须回退到规则或澄清。

## 12. M7：混合控制和角色生态

### 12.1 目标

让语音、模仿、舞蹈包、角色和皮肤在同一个运行时中协同。

### 12.2 交付物

- `CommandArbiter`。
- 动作层掩码。
- 模仿与根运动冲突规则。
- 舞蹈和模仿切换规则。
- 皮肤切换和动作互不干扰。
- 安全保持。
- 摄像头恢复。
- 云端网络恢复。
- 多角色切换。
- 角色能力降级。
- 皮肤在模仿中热切换。
- 字幕和状态面板完整反馈。

### 12.3 进入条件

- M4 实时模仿稳定。
- M6 本地和云端语音链路稳定。
- M3 皮肤切换稳定。
- 所有动作都有骨骼掩码和优先级。

### 12.4 退出条件

- 全身模仿时拒绝不安全的根运动。
- 上半身模仿时允许根运动。
- 舞蹈播放中换肤不断开动作。
- 紧急停止可打断任何状态。
- 摄像头丢失自动安全保持。
- 恢复后不闪回错误姿态。
- 云端超时不阻塞本地控制。
- 机器人指挥中心和训练页互不争抢资源。

## 13. M8：评价、游戏化和回放整合

### 13.1 目标

### 13.2 交付物

- 音乐主时钟。
- 速度调节。
- 321 倒计时。
- OK 手势开始。
- 实时评分。
- 身体部位得分。
- 手势和人脸客观特征融合。
- 连击、失误和趋势。
- 片段重练。
- 训练总结。
- 专业教练、技术裁判、初学者和游戏主持模板。
- JSON 结构化 LLM 评价。

### 13.3 进入条件

## 14. M9：性能、隐私与发布硬化

### 14.1 目标

让项目在比赛和低端设备上可稳定展示。

### 14.2 交付物

- 6GB 显存预算报告。
- P0 至 P3 性能档位。
- 自动降级和滞回。
- 30 分钟稳定性测试。
- 摄像头和音频恢复测试。
- 离线资源检查。
- 打包资源检查。
- 皮肤和模型许可证清单。
- 隐私模式。
- 日志脱敏。
- 错误恢复矩阵。
- 比赛演示脚本。
- 备份数据导出。

### 14.3 进入条件

- M7 混合控制稳定。
- M8 评价链路可用。
- 所有核心资源本地化。

### 14.4 退出条件

- 目标设备连续运行 30 分钟无崩溃。
- 显存无持续增长。
- 断网仍能完成本地训练和指挥。
- 原始视频和音频默认不上传。
- API Key 不写入日志。
- 皮肤、角色、音乐和动作许可证清晰。
- 低端设备可完成完整流程。
- 包装产物包含 WebEngine、SVG、资源和权重隐藏依赖。
- 演示失败时有本地骨架和安全指挥回退。

## 15. 可并行工作流

### 15.1 可以并行

- M2 的动作包解析与 M3 的角色加载。
- M5 的手部规则与 M6 的本地语音规则。
- M3 的皮肤卡片 UI 与 M4 的 Pose 总线。

### 15.2 不可以并行合并

- 不让两个模块各自启动摄像头和 YOLO。
- 不让两个模块直接写同一角色骨骼。
- 不让语音和模仿都拥有独立三倍缓冲。
- 不让皮肤切换重建角色。
- 不让 LLM 直接产生骨骼旋转。
- 不在实时循环中做网络请求和数据库写入。

## 17. 第一实施切片

用户确认后，第一切片只做：

- M0 契约冻结。
- M1 的 ActorRuntime 和 StageRuntime 基础。
- 单角色、单舞台、米制根节点。
- 自动取景和安全边界。
- `PoseFramePacket` 空实现或模拟数据。
- `MotionIntent` 空实现或模拟数据。
- `RuntimeMetrics` 采集。
- 原生骨架和 Three.js 回退。
- 现有训练页兼容验证。

第一切片不做：

- 真实机器人皮肤包。
- 云端 LLM 复杂规划。
- 多人模式。
- SMPL-X。
- 高精度 IK。
- 手部和人脸实时推理。
- 自动下载角色。

第一切片成功的标志是：

- 角色单位、根节点、相机和舞台边界稳定。
- 训练页不回归。
- Worker 和 WebEngine 生命周期稳定。
- 后续姿态、语音和皮肤模块可以接入同一个运行时。

## 18. 风险登记

| 风险 | 阶段 | 影响 | 对策 |
|---|---|---|---|
| 数据契约频繁变化 | M0-M4 | 重写成本高 | 版本号和兼容层 |
| 角色骨架不统一 | M3-M4 | 动作错位 | Humanoid 契约和测试动作 |
| 重复运行模型 | M4-M6 | 显存和延迟上升 | 单 PoseFrameBus |
| 动作互相覆盖 | M7 | 机器人抖动 | 单写入者和骨骼掩码 |
| 皮肤资源泄漏 | M3-M9 | 显存持续增长 | LRU、引用计数、30 分钟测试 |
| 手部抢占 GPU | M5 | 全身掉帧 | ROI、低频、可关闭 |
| ASR 误识别 | M6 | 执行错误命令 | 白名单、置信度、澄清 |
| LLM 幻觉 | M6-M8 | 危险动作 | 本地校验、Schema、拒绝 |
| 摄像头环境变化 | M4-M9 | 构图失败 | 校准、质量等级、安全保持 |
| 低端设备不足 | M9 | 卡顿 | 档位、降级、骨架回退 |
| 比赛断网 | M6-M9 | 云端不可用 | 本地安全通道和本地资源 |
| 许可证不清 | M2-M9 | 无法发布 | 资源清单和默认 CC0 |
| IP 模型分发 | M3 | 法律风险 | 用户本地导入，不打包 |
| IP 地址或 API Key 泄漏 | M9 | 安全问题 | 日志脱敏和本地配置 |
| 主线程阻塞 | M1-M9 | 界面冻结 | Worker 和信号桥 |

## 19. 发布门槛

### 19.1 功能门槛

- 舞蹈包选择和播放可用。
- 实时模仿可用。
- 语音指挥可用。
- 皮肤切换可用。
- 评分和总结可用。
- 摄像头丢失可恢复。

### 19.2 性能门槛

- 3060 6GB 平衡档稳定。
- 低端档可完成完整流程。
- 无持续显存泄漏。
- 无无限队列。
- 无主线程长时间阻塞。

### 19.3 隐私门槛

- 原始视频默认不上传。
- 原始音频默认不保存。
- 人脸默认关闭。
- 日志不含密钥。
- 用户可删除本地动作、录像、皮肤和历史。

### 19.4 许可证门槛

- 代码依赖许可证明确。
- 默认模型许可证明确。
- 默认皮肤许可证明确。
- 音效和音乐许可证明确。
- 用户导入资产有隔离策略。
- 不随项目分发无授权 IP 模型。

### 19.5 稳定性门槛

- 连续开始停止 50 次无崩溃。
- 连续换肤 20 次无泄漏。
- 摄像头断开恢复 20 次。
- 网络断开恢复 20 次。
- 关闭窗口时所有 Worker 正常退出。

## 20. 最终交付定义

项目最终应达到：

1. 用户可以从舞蹈包大厅选择舞蹈。
2. 视频可以转换为可保存的 3D 动作包。
3. 训练页可以双舞台比较。
4. 机器人指挥中心可以用语音控制机器人。
5. 机器人可以实时模仿摄像头前的人。
6. 用户可以实时切换角色和皮肤。
7. 动作、音乐、字幕、评分和 TTS 使用统一时间轴。
8. 云端 LLM 只做结构化解释和规划，不控制骨骼。
9. 6GB 显存设备可以自动降级并稳定运行。
10. 比赛现场断网时，本地核心功能仍可用。
11. 默认资源许可证清晰。
12. 代码、文档、测试和资源边界一致。

这份路线图的目的，是让项目从“功能列表”进入“可交付系统”。每次开发只推进一个可验收切片，不靠界面掩盖底层冲突，不靠高配设备掩盖性能问题，也不把安全、隐私和许可证留到比赛前一天处理。
