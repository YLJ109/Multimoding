## 0. 结论先行

V5 要把项目的多模态能力升级为四层：

1. **感知层**：YOLO Pose 负责全身，MediaPipe Hands 负责手部，MediaPipe Face 负责面部和头部，音频引擎负责音乐和节拍。
2. **结构化特征层**：把视频和摄像头结果转换为可计算、可测试、可保存的数值特征，不直接把原始画面交给 LLM。
3. **本地决策层**：评分、节奏、动作比较、错误优先级、语音提醒全部本地完成。
4. **语言评价层**：云端 LLM 只读取结构化摘要，根据固定提示词模板输出专业、多维度、可验证的训练评价。

必须坚持三条边界：

- LLM 不计算动作分数，不估计关节角度，不负责实时安全判断。
- 人脸用于头部朝向、表情、可见性和训练状态，不做身份识别，不诊断心理或医学状态。
- 手势用于准备确认、开始/暂停、答题或交互，不把偶然手势直接当作游戏控制。

官方 Python 包名通常是 `mediapipe`，不是 `mediapypi`。具体安装版本和模型文件必须在 `pytorch_cuda_env` 内单独验证，不能假定现有环境已经支持。

## 1. V5 完整链路

```text
摄像头 / 视频
  -> 人体检测和跟踪
  -> YOLO Pose 全身关键点
  -> 主人物裁剪
  -> MediaPipe Hands 手部 21 点
  -> MediaPipe Face 人脸和头部特征
  -> 时间同步和置信度融合
  -> 手势状态机
  -> 人脸状态和头部朝向
  -> 动作、节奏、稳定性、表情、手势综合评分
  -> 训练结构化摘要
  -> LLM 提示词模板
  -> 专业评价、训练计划、薄弱片段
  -> 结果页、TTS 摘要和历史趋势
```

实时训练期间：

- LLM 不参与每一帧。
- 手部和人脸模型低频运行。
- 只发送结构和统计，不发送连续视频流。
- LLM 失败时本地报告仍然完整。

## 2. 多模态模块划分

### 2.1 全身姿态

来源：

- YOLO Pose。
- COCO-17。
- 归一化、平滑、三维提升和角色重定向。

职责：

- 主要动作评分。
- 左右手、左右腿、躯干、重心和脚步。
- 角色动画驱动。
- 动作失误定位。

### 2.2 手部特征

来源：

- MediaPipe Hand Landmarker。
- 每只手 21 个关键点。
- 可选世界坐标、手别、置信度和跟踪 ID。

职责：

- OK 手势。
- 张开手掌。
- 握拳。
- 大拇指点赞。
- 比心。
- V 手势。
- 指向。
- 拍手节奏。
- 手指伸展和捏合特征。

### 2.3 人脸和头部

来源：

- MediaPipe Face Landmarker。
- 面部关键点、混合形状、头部姿态。
- 可选眼睛、眉毛、嘴部和下颌信息。

职责：

- 是否看到人脸。
- 头部左右转动、上下俯仰和倾斜。
- 眨眼和眼睛可见性。
- 张嘴、微笑和表情变化。
- 用户是否正对摄像头。
- 用户是否长时间低头或转身。
- 结算时作为表现力或投入度参考，不作为主要分数。

### 2.4 音频

来源：

- 音乐播放器主时钟。
- 节拍检测。
- 可选麦克风节拍特征。

职责：

- 拍点同步。
- 动作起拍和落拍。
- 节奏评分。
- 倒计时与音乐对齐。
- 可选掌声或人声节奏反馈。

## 3. MediaPipe 方案

### 3.1 组件选择

建议使用：

- MediaPipe Tasks Vision。
- Hand Landmarker。
- Face Landmarker。
- Pose Landmarker 作为 YOLO 的备用或辅助，不作为默认主姿态模型。

原因：

- YOLO Pose 已经接入项目，负责主评分。
- MediaPipe Hands 和 Face 更适合局部特征。
- 局部模型只处理人物裁剪，不重复处理整张高分辨率画面。

### 3.2 运行策略

| 模块 | 默认频率 | 运行阶段 | 低端策略 |
|---|---:|---|---|
| YOLO Pose | 12 至 20 FPS | 全程 | 8 至 12 FPS |
| Hand Landmarker | 4 至 10 FPS | 准备、倒计时、指定交互 | 3 至 6 FPS |
| Face Landmarker | 3 至 8 FPS | 准备、关键帧、结算 | 2 至 4 FPS 或关闭 |
| 音频节拍 | 播放器时间轴 | 全程 | 全程 |
| LLM | 训练结束一次 | 结算 | 结束一次 |

### 3.3 主人物裁剪

先由 YOLO 得到主人物框：

- 头部区域用于 Face。
- 左右腕区域用于 Hands。
- 手腕不可见时扩大搜索区域。
- 多人画面只分析主人物。
- 室友和其他人不进入手部、人脸特征。

### 3.4 后端设备

- 手部和人脸模型优先使用 CPU 或轻量设备代理，避免抢占 YOLO 的 GPU 资源。
- 支持 GPU 代理时再启用，不能假定 Python Windows 环境一定支持。
- 如果 MediaPipe GPU 路线不稳定，保留 CPU 方案。
- 模型和 OpenCV、NumPy、Protobuf 版本必须锁定。
- 比赛版本必须在目标电脑上做一次真实性能测试。

### 3.5 模型文件

- 手部和人脸模型文件本地保存。
- 启动时不从网络下载。
- 保存模型版本、许可证和 SHA-256。
- 模型缺失时只关闭对应多模态模块，不阻塞全身训练。
- 低端模式可以只保留 OK 手势，关闭人脸分析。

## 4. 手势识别系统

### 4.1 手部关键点

每只手得到 21 个点：

- 腕。
- 拇指 4 点。
- 食指 4 点。
- 中指 4 点。
- 无名指 4 点。
- 小指 4 点。

可用特征：

- 手指伸展度。
- 手指弯曲角度。
- 指尖到掌心距离。
- 拇指到食指距离。
- 手掌方向和旋转。
- 手掌大小归一化。
- 左右手。
- 手部置信度。

### 4.2 手势分类

基础手势：

- OK：拇指和食指闭合，其余手指伸展。
- 张开手掌：五指伸展。
- 握拳：多数手指弯曲。
- 点赞：拇指伸展，其他手指闭合。
- V 手势：食指和中指伸展。
- 比心：双手交叉组合。
- 指向：食指伸展，其他手指闭合。
- 拍手：双手距离周期缩短。

### 4.3 手势状态机

```text
未检测
检测中
保持中
确认
误触
保持过短
超出画面
模型不可用
```

进入确认需要：

- 手势类别置信度达标。
- 保持时间达标，通常 0.8 至 1.2 秒。
- 手腕和手掌在画面内。
- 全身状态允许。
- 同一手势有冷却时间。

### 4.4 手势用途

必须由用户明确触发的功能：

- OK：准备完成，开始倒计时。
- 大拇指：确认选择或提交。
- 张开手掌：打开菜单或请求暂停，必须二次确认。
- 握拳：静音或暂停，必须二次确认。
- V：进入挑战模式。
- 比心：收藏当前舞蹈包或点赞教练建议。

不允许：

- 单帧识别就触发暂停。
- 随机挥手停止训练。
- 把不清晰手势当作评分错误。
- 将手势用于身份识别或权限控制。

### 4.5 手势与 3D 角色

- 用户做 OK 时，系统只确认准备。
- 如果用户角色支持手指骨骼，可以让角色回应一个 OK 手势。
- 如果不支持手指，只显示 UI 反馈。
- 手势结果不改变动作评分，除非舞蹈包明确包含手指动作。

## 5. 人脸与头部特征

### 5.1 可用特征

- 人脸是否存在。
- 人脸位置和大小。
- 头部左右转向。
- 头部上下俯仰。
- 头部倾斜。
- 眼睛可见性。
- 眨眼频率。
- 张嘴程度。
- 微笑程度。
- 眉毛和下颌变化。
- 面部遮挡。
- 面部置信度。

### 5.2 在舞蹈训练中的用途

- 准备阶段：确认正对摄像头、头部可见、脸部没有被遮挡。
- 倒计时：判断用户是否看向屏幕。
- 舞蹈中：评估头部朝向是否跟上动作。
- 表情表现：作为表现力附加分，不作为主要动作分。
- 结果页：给出“头部方向”“表情投入”“视线状态”的客观描述。
- 交互：微笑触发庆祝、点头确认等，必须可选。

### 5.3 评分权重

建议：

- 全身姿态和音乐节奏占主要分数。
- 头部朝向最多 5%。
- 表情和微笑最多 3%。
- 不将眼睛大小、嘴型或面部特征与年龄、性别、情绪或人格判断绑定。
- 用户可以选择关闭表情分析。

### 5.4 隐私红线

- 不提取或保存人脸身份向量。
- 不尝试识别人名。
- 不上传原始人脸图像。
- 不将脸部特征用于广告、社交或跟踪。
- 本地日志不得保存完整人脸关键点历史。
- 结算报告只保存聚合特征，例如“正面朝向占 82%”。

## 6. 多模态时间融合

### 6.1 时间对齐

不同模型频率不同：

- YOLO 15 FPS。
- Hands 8 FPS。
- Face 5 FPS。
- 音频时间轴连续。

融合策略：

- 以音乐主时钟作为基准。
- 每类特征带自己的时间戳。
- 对最近邻或插值结果进行融合。
- 不同模态允许少量延迟。
- 置信度低时不参与最终评分。
- 缺失模块不阻塞其他模块。

### 6.2 特征融合

统一特征包可以包括：

- 身体姿态特征。
- 手势特征。
- 人脸和头部特征。
- 音乐和节拍特征。
- 用户画面质量。
- 隐私和多人状态。
- 设备性能状态。

### 6.3 冲突处理

如果身体显示手抬起，但手部模型没有检测到：

- 优先使用身体腕关节。
- 降低手指特征权重。
- 标记手部不确定。
- 不直接扣分。

如果人脸显示转头，但身体朝前：

- 以姿态为准，头部特征单独记录。
- 不作为动作失败的主要依据。

### 6.4 平滑

- 手势使用状态机，不逐帧抖动。
- 人脸参数使用短时滑动窗口。
- 头部姿态使用低通滤波。
- 多模态时间差超过阈值时显示“暂时无法判断”。

## 7. 视觉模块的代码边界

建议目录：

```text
src/dance_mirror/
  multimodal/
    contracts.py         多模态纯数据定义
    fusion.py            时间对齐和特征融合
    temporal.py          滑动窗口和状态机
    quality.py           置信度、遮挡和质量报告

  vision/
    hands/
      engine.py          MediaPipe Hand 适配
      gestures.py        手势规则和状态机
      landmarks.py       手部点处理和归一化
    face/
      engine.py          MediaPipe Face 适配
      features.py        头部、眼睛、嘴部和表情特征
      privacy.py         人脸特征脱敏
    pose/
      engine.py          YOLO Pose 适配
      roi.py             主人物裁剪区域

  feedback/
    summary.py           结构化训练摘要
    llm_client.py        云端 LLM 调用
    prompt_registry.py   提示词模板加载和版本管理
    schema.py            输出结构校验
    fallback.py          本地模板回退
    tts_script.py        短语音稿生成
```

职责原则：

- `vision` 只产生特征。
- `multimodal` 只做融合。
- `feedback` 只做摘要和语言生成。
- `view` 不直接调用 MediaPipe。
- `workers` 不包含评分算法。
- LLM 不依赖原始摄像头画面。

## 8. LLM 评价系统

### 8.1 为什么不能直接上传视频

不推荐：

- 成本高。
- 延迟高。
- 隐私风险大。
- 数值不稳定。
- 非实时任务不需要视频。
- 单帧视觉模型无法可靠判断完整舞蹈过程。

正确方式：

- 本地计算分数和统计。
- 发送结构化摘要。
- LLM 负责解释、归纳、计划和建议。
- 结果与本地分数保持一一对应。

### 8.2 LLM 输入

包含：

- 舞蹈包名称、舞种、难度、速度。
- 本次训练时长。
- 总分、等级、星级。
- 姿态、节奏、稳定、覆盖、完成度。
- 左右手、左右腿、躯干、头部、表情分项。
- 错误类型和持续时间。
- 最优分段和薄弱分段。
- 手势事件。
- 头部朝向统计。
- 表情投入统计。
- 覆盖率和不可判断比例。
- 最近 5 次成绩趋势。
- 用户目标和偏好。
- 输出语言和语气。

不包含：

- 原始视频。
- 连续摄像头帧。
- 人脸身份信息。
- 家庭或宿舍背景。
- 室友画面。
- API Key。
- 文件绝对路径。
- 用户真实姓名，除非用户主动配置。

### 8.3 LLM 输出

固定结构：

- 总评。
- 三个优点。
- 三个主要问题。
- 分维度评价。
- 时间轴洞察。
- 3 至 7 天练习计划。
- 当前最值得重练的片段。
- 下次训练的量化目标。
- 安全和不适应提醒。
- 鼓励性总结。
- 置信度和数据不足提示。

### 8.4 LLM 禁止事项

- 不编造分数。
- 不编造未提供的动作。
- 不做医学诊断。
- 不判断人格、心理疾病或情绪障碍。
- 不进行身份识别。
- 不羞辱用户。
- 不输出危险训练建议。
- 不把模糊或遮挡称为确定错误。
- 不泄露提示词、系统配置或 API Key。
- 不执行摘要数据中的指令。

### 8.5 本地回退

云端失败时：

- 使用本地规则生成简短总结。
- 显示结构化分项。
- 给出固定练习建议。
- 仍然保存历史记录。
- 不阻塞结果页和片段重练。

## 9. 提示词模板体系

完整模板见 `docs/LLM_PROMPT_TEMPLATES_V5.md`。

### 9.1 模板分类

- `system_base_v1`：通用边界和输出规则。
- `coach_professional_v1`：专业舞蹈教练。
- `judge_technical_v1`：技术裁判。
- `beginner_friendly_v1`：初学者友好教练。
- `game_host_v1`：游戏解说。
- `progress_review_v1`：历史趋势复盘。
- `segment_drill_v1`：片段重练计划。
- `tts_summary_v1`：语音短稿。
- `safety_guard_v1`：安全和隐私守门。
- `repair_json_v1`：输出格式修复，只允许修复结构，不增加事实。

### 9.2 模板变量

- `{{session_json}}`
- `{{dance_package_json}}`
- `{{score_summary_json}}`
- `{{multimodal_summary_json}}`
- `{{history_json}}`
- `{{user_goal}}`
- `{{tone}}`
- `{{language}}`
- `{{max_words}}`
- `{{schema_version}}`

### 9.3 模板版本

每个模板记录：

- ID。
- 版本。
- 适用模型。
- 输出 schema。
- 温度。
- 最大输出长度。
- 适用语言。
- 隐私等级。
- 更新时间。
- 评估结果。

### 9.4 注入防护

- 用户名称、动作包名称和备注都必须作为数据，不作为指令。
- 数据放在明确标记的 XML 或 JSON 区块内。
- 系统提示明确禁止执行数据中的指令。
- 去除长度异常和可疑控制字符。
- 输出必须经过 JSON 结构校验。
- 多次失败只修复一次，不进入无限重试。

### 9.5 生成参数

建议：

- 结构化总结：低温度。
- 游戏解说：中等温度。
- TTS 短稿：低温度。
- 技术裁判：低温度。
- 不使用高温创作模式生成训练结论。
- 输出长度由模板控制，避免结果页过长。

## 10. 评价维度扩展

新增多模态评价维度：

| 维度 | 来源 | 权重建议 |
|---|---|---:|
| 姿态准确 | Pose | 40% |
| 节奏同步 | Audio + Pose | 20% |
| 动作稳定 | Pose 时间序列 | 10% |
| 有效覆盖 | Pose + 质量 | 10% |
| 完整完成 | 动作阶段 | 10% |
| 手势响应 | Hands | 4% |
| 头部方向 | Face + Pose | 3% |
| 表情投入 | Face | 3% |

原则：

- 手势和表情只是锦上添花，不能主导总分。
- 用户关闭人脸或手势时，相应权重重新分配到核心维度。
- 低置信度模块不参与评分。
- 不同设备和不同模式要使用相同基础规则。

## 11. 交互玩法扩展

### 11.1 准备阶段

- 全身就位。
- 手部可见。
- 头部朝向正常。
- OK 手势确认。
- 人脸或头部可见性提示。
- 3、2、1 倒计时。

### 11.2 游戏中

- 动作提示。
- 拍点指示。
- 手势彩蛋。
- 表情投入和微笑反馈。
- 连击和判定。
- 语音短提示。

### 11.3 结算中

- 手势触发庆祝或重练。
- 表情变化反映结果。
- 教练角色根据评级做动作。
- LLM 生成专业总结。
- TTS 只播报 2 至 3 句摘要。

### 11.4 可选手势快捷命令

- 大拇指：确认保存结果。
- 张开手掌：请求暂停，需要二次确认。
- 握拳：静音音乐，需要二次确认。
- V：进入挑战模式。
- 比心：收藏当前舞蹈包。

## 13. 隐私与安全

### 13.1 默认设置

- 手势默认开启。
- 人脸默认只做技术特征，不做身份识别。
- 表情分析默认关闭或首次询问。
- 麦克风默认关闭。
- 原始视频默认不上传。
- 训练录像默认不保存。

### 13.2 明确同意

开启人脸或麦克风时需要告知：

- 处理哪些数据。
- 是否只在本地处理。
- 是否发送摘要到云端。
- 如何关闭和删除。
- 不会识别人名。
- 不会推断敏感属性。

### 13.3 日志

- 不记录原始人脸点击点。
- 不记录完整手部点击点。
- 日志只记录事件类型和聚合计数值。
- API Key 不写入日志。
- 云端请求记录不保存完整个人内容。

### 13.4 比赛

- 比赛现场默认离线。
- 云端 LLM 可选。
- 多模态模块可单独关闭。
- 展示时说明哪些处理在本地，哪些发送到云端。

## 14. 低端设备性能策略

### 14.1 分层策略

| 配置 | Pose | Hands | Face | LLM |
|---|---|---|---|---|
| 高 | 15 至 20 FPS | 8 至 10 FPS | 5 至 8 FPS | 结算 |
| 平衡 | 12 至 15 FPS | 5 至 8 FPS | 3 至 5 FPS | 结算 |
| 低 | 8 至 12 FPS | 3 至 5 FPS | 2 至 3 FPS | 结算 |
| 极低 | 6 至 8 FPS | 准备阶段 3 FPS | 关闭 | 结算或本地 |

### 14.2 局部裁剪

- 不把整张 1080p 图片反复送给三个模型。
- 先由 Pose 找到人物。
- 只裁剪头、手和身体区域。
- 手部使用手腕周围 ROI。
- 面部使用头部上方 ROI。
- 无人或关节不可见时跳过局部推理。

### 14.3 生命周期

- 准备阶段运行 Hands 和 Face。
- 进入正式舞蹈后降低频率。
- 结果页不再运行 Hands 和 Face。
- 退出页面后释放任务模型。
- 长时间无手势时暂停模型。
- 不把 LLM 放在实时闭环。

### 14.4 自动降级

1. 降低 Face 频率。
2. 关闭表情分析。
3. 降低 Hands 频率。
4. 关闭非关键手势。
5. 保留 OK 手势回退。
6. 关闭摄像头人脸特征，只保留 Pose。
7. 使用本地规则报告。

## 17. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| MediaPipe 兼容性 | 安装失败或崩溃 | 独立环境验证，锁版本，保留回退 |
| 手部模型误触 | 游戏突然暂停 | 状态机、保持时间、二次确认 |
| 人脸隐私风险 | 用户不接受 | 本地处理、关闭开关、不存原图 |
| 人脸错误推断 | 评价不专业 | 只做客观特征，不做心理诊断 |
| 多模型抢占 GPU | YOLO 卡顿 | Hands/Face 低频、ROI 裁剪、CPU 优先 |
| 多模态时间错位 | 评分不一致 | 音乐主时钟，时间戳融合 |
| LLM 幻觉 | 编造错误 | 结构化输入、强约束模板、schema 校验 |
| 输出 JSON 不稳定 | 页面无法解析 | 低温度、JSON 模式、一次修复、本地回退 |
| 提示词注入 | 改变模型行为 | 数据隔离，禁止执行输入中的指令 |
| 低端设备过慢 | 掉帧 | 分级频率和模块自动关闭 |
| 模型文件丢失 | 功能不可用 | 离线模型包、哈希和完整性检查 |

## 18. 最终推荐优先级

1. 先验证 MediaPipe 在 `pytorch_cuda_env` 和目标电脑上的兼容性。
2. 实现手部 21 点和 OK 手势，优先服务准备流程。
3. 实现人脸可见性和头部朝向，不默认做表情判断。
4. 建立多模态统一时间戳和融合层。
5. 在现有评分基础上增加头部、手势和表情的低权重维度。
6. 建立结构化训练摘要。
7. 接入 LLM 提示词模板和 JSON 校验。
8. 做本地回退、结果页、TTS 和低端设备降级。
9. 最后做长期隐私审计和比赛离线验证。

最终产品不是“让大模型随便点评”，而是：

**本地多模态精准判断，本地评分可解释，云端大模型只负责把事实总结成专业、分维度、可执行的舞蹈训练建议。**
