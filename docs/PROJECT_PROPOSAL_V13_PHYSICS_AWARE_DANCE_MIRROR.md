## 2. 研究问题（Research Questions）

- **RQ1**　单目 RGB 条件下，如何检测并保持"脚—地接触"，以消除重定向中的脚滑与穿地？
- **RQ2**　如何把舞蹈质量分解为**可测量、可解释、与人类主观评分一致**的多个维度？
- **RQ3**　差异驱动的自动示范，能否在有限训练轮次内显著提升学习者的动作评分（闭环有效性）？

> 答辩时先讲 RQ，再讲方法，再讲实验——这是"研究型毕设"的标准骨架，比"我做了个 App"高一个层级。

## 3. 创新点详解

### 创新点 1 ★ 接触感知的舞蹈重定向（Contact-Aware Retargeting）

**现状痛点**：纯几何对齐只保证"骨骼方向正确"，不保证"物理合理"。脚踝跟着小腿旋转 → 站立时脚在滑、抬腿时脚穿地、换重心时整人飘。

**方法（三阶段）**：

| 阶段 | 做法 | 关键设计 |
|---|---|---|
| **a. 接触检测** | 用脚踝关键点的**高度 + 速度 + 悬空时长**做带滞回的接触状态机 | 滞回阈值避免抖动；输出"接触概率"而非硬 0/1 |
| **b. 脚锁定 (Foot Locking)** | 接触相位内**固定脚的世界位置**，把踝关节位移归零，反向调整髋/膝（解析 IK） | 只在接触相位生效，摆动相位自由 |
| **c. 平衡约束** | 重心地面投影须落在**支撑多边形**内，否则施加最小位移的躯干修正 | 用"支撑脚为参考系"归一化，规避单目无绝对尺度 |

**可量化指标（论文出图）**：脚滑量 (cm/frame)、穿地深度 (cm)、重心越界率 (%)、修正幅度 (cm)。
**实验设计**：同一段舞蹈，**纯几何 vs 接触感知**，指标前后对比 + 主观观感打分。
**边界声明（答辩要主动说）**：不做全物理仿真（无动力学、无摩擦模型），只做**运动学可行性约束**——这是可控且诚实的范围。

---

### 创新点 2 ★ 四维表现力评估模型

**现状痛点**：只算"位置像不像"，无法解释"为什么这段跳得没感觉"。

| 维度 | 测什么 | 方法 |
|---|---|---|
| ① 姿态相似 | 关节角度/位置 | 归一化空间 + 加权关节误差 |
| ② **节奏相位对齐** | 是否踩在拍上（早/晚） | 节拍跟踪 → 相位估计 → **相位域对齐**替代朴素 DTW |
| ③ **动力学** | 力度、延伸、收放 | 速度/加速度峰值、动作幅度包络 |
| ④ **流畅度** | 卡顿、犹豫 | jerk（加加速度）与停顿检测 |

**可量化**：与 3 位人类评审评分的 **Spearman 相关系数**；**分维消融实验**（去掉某一维，相关性如何变化）。
**输出**：可解释雷达图 + "你这段的问题是抢拍 0.18s、手臂延伸不足"级别的具体反馈。

---

### 创新点 3 ★ 差异驱动的自动示范（闭环关键）

**输入**：你的动作 vs 标准动作的差异（**分关节**、**分阶段**）。
**输出**：
1. 3D 机器人**分段慢放示范**（只播你出错的段落）；
2. **高亮差异关节**（红/绿对比）；
3. LLM 生成的自然语言讲解（接你现有的云端教练 + 本地白名单校验）。

**可量化**：闭环有效性 —— **示范前 → 示范后**的评分提升曲线，对照"只看回放不给示范"的控制组。

---

### 创新点 4（可选加分）舞蹈动作资产库

动作包格式**版本化**（`schema_version`）+ 质量元数据（质量置信度 / BPM / 难度 / 风格）→ 支持按条件检索（"给我一个 BPM 120、难度中、质量 A 的 8 拍组合"）。

## 4. 系统架构

```
┌────────────────── Vue 3 前端（新增） ──────────────────┐
│  界面组件(Vue+TS) │ 摄像头采集(getUserMedia) │ 3D(Three.js) │
└───────────────┬───────────────────────────────────────┘
        HTTPS (REST)  │  WebSocket (实时姿态/评分流)
┌───────────────▼───── FastAPI 后端（新增） ─────────────┐
│  接口层(REST) │ 实时通道(WS) │ 任务编排(长任务队列)      │
└───────────────┬───────────────────────────────────────┘
        进程内直接调用（不重写算法）
┌───────────────▼──── Python 算法层（复用+重构）────────┐
│ 姿态推理 │ 接触感知重定向 │ 表现力评估 │ 示范生成 │ 存储 │
└───────────────────────────────────────────────────────┘
```

| 层 | 选型 | 理由 | 备选 |
|---|---|---|---|
| 前端 | **Vue 3 + TS + Vite + Three.js + Pinia** | 你已熟悉；3D 场景现成可搬 | React |
| 后端 | **FastAPI + WebSocket + Pydantic v2** | 你已熟悉；**自动 OpenAPI + 自动 TS 类型** | Node/NestJS |
| 算法 | MediaPipe BlazePose（真 3D world landmarks）+ YOLO11-pose 兜底 | 复用现有能力，21ms 级实时 | MMPose |
| 数据 | SQLite（本地）/ Postgres（服务器） | 离线可用 | — |
| 长任务 | asyncio 队列 / ARQ | 视频分析是分钟级任务 | Celery |
| 测试 | pytest + vitest + （可选）Playwright | 契约 + 接缝 + E2E | — |

**架构纪律（直接吸取旧版教训）**：
1. **单一管线**：`FramePipeline.process(frame) -> FrameResult`，桌面/Web 共用。
2. **契约单一真源**：Pydantic 模型是唯一真源 → 自动导出 TS 类型，**禁止手写两份**。
3. **接缝测试**：跨语言边界必须双向断言（Python 造 fixture + TS 消费断言）。
4. **不写上帝对象**：会话状态机独立成类，可纯单测。

## 5. 数据与契约设计（旧版踩过的坑，这里根治）

### 5.1 payload / API 契约
```
Pydantic v2 模型 ──自动──> OpenAPI ──自动──> TS 类型（前端 import）
```
- **禁止**手工维护两份类型定义。
- **版本化**：每个 payload 带 `schema_version`；前端首行校验，不匹配则**降级并提示**，绝不崩。
- **实时帧**：WebSocket 用**二进制**（float32 关键点数组）或 MessagePack，而不是每帧 JSON —— 省带宽、降延迟。

### 5.2 动作包格式 `.dmotion`（v1）
```
{ schema_version: 1, meta: {bpm, difficulty, style, quality},
  frames: <binary float32 [T,17,3]>,
  scores: <binary float32 [T,17]>,
  hand_landmarks: [...] }
```
- 关键点用二进制而非 JSON 索引对象（**旧版 hands 对象/数组不一致的根因**）。

## 6. 端到端核心流程

```
1. 采集    摄像头帧（30fps）
2. 推理    BlazePose → COCO-17（pose3d 真实米制 + pose2d 像素）
3. 归一化  髋中心为原点 / 躯干为单位（镜像 = 换标签 + 翻 x，保持真反射）
4. 重定向  接触检测 → 脚锁定 → 平衡修正 → 骨骼目标
5. 评估    四维打分 + 差异定位（分关节/分阶段）
6. 反馈    3D 示范分段慢放 + 高亮差异关节 + LLM 讲解
7. 再练    评估提升 → 训练记录 → 动作资产沉淀
```

---

## 7. 闭环设计（本方案的"完美闭环"）

**学 → 评 → 纠 → 再学 → 沉淀**，每一环都有**可测量的输出**，而不是走个流程：

| 环节 | 输出 | 可测指标 |
|---|---|---|
| 学 | 实时重定向骨骼 | 延迟 (ms)、脚滑量 |
| 评 | 四维评分 + 差异定位 | 与人工评分相关性 |
| 纠 | 分段示范 + 高亮 + 讲解 | 示范前/后评分差 |
| 再学 | 新一轮训练 | 收敛所需轮次 |
| 沉淀 | 动作包 + 质量元数据 | 资产库可检索性 |

## 9. 实验设计与评估（论文的核心，别省）

- **数据集**：自采（授权可控）+ 公开数据集（如 AIST++/FineDance，**注意许可**）。
- **基线对比**：纯几何重定向（旧法）vs 接触感知（新法）。
- **指标表**：脚滑量 / 穿地深度 / 重心越界率 / 评分相关性 / 闭环提升。
- **消融实验**：去掉脚锁定、去掉平衡约束、去掉节奏维度分别如何 —— **这是评委最认的部分**。
- **主观实验**：3–5 位人类评审打分，算 Spearman。

## 13. 建议的启动顺序

1. **先做 P0–P2 护栏**（接缝测试 / 合并双份管线 / payload 契约）—— 无论新旧架构都必须做，且能立刻止住"改一处崩一处"。
2. **再验证创新点 1 的最小可行版**（接触检测 + 脚锁定，先不接前端，用离线数据出指标图）。
3. **指标成立后**，再启动 Vue 前端与 FastAPI 服务层。
4. **最后**做示范闭环与实验。

> 这样每一步都有可交付、可验证的产物，不存在"写了一半发现方向不对"的返工。
