## 0. 结论先行

V4 要把角色从“一个写死的低模人体”升级成完整的角色生态：

1. **可内置角色**：机器人、低模真人比例角色、卡通舞者、机甲、原创英雄、吉祥物、教练角色。
2. **用户导入角色**：GLB、GLTF、VRM，可以由用户本地导入蜘蛛侠、奥特曼、动漫人物、自定义人物等模型。
3. **IP 边界**：未经授权，项目不能随安装包分发蜘蛛侠、奥特曼等受版权和商标保护的模型。应用可以支持本地导入，但不能把模型打包、上传或随舞蹈包导出。
4. **统一骨架层**：所有角色都转换到统一 Humanoid 骨骼规范，动作先重定向到统一骨骼，再映射到模型，禁止每个模型单独写一套动作逻辑。
5. **角色变体**：同一角色支持颜色、材质、体型、服装、配件和表情变体，减少重复模型和下载体积。
6. **多角色分工**：标准舞者、用户角色、教练角色、幽灵对照、伴舞角色和装饰角色可以独立配置。
7. **低端设备回退**：高端显示完整模型，中端使用低模，低端自动切骨架或简化角色，但训练、音乐、评分和流程不降级。
8. **专业实现链路**：模型发现、校验、加载、克隆、骨骼映射、重定向、约束、LOD、缓存和释放全部模块化。

最终形态不是一个“模型下拉框”，而是一套可扩展的角色引擎。

## 1. 用户提出的角色需求与处理方式

| 需求角色 | 项目内置 | 用户本地导入 | 风险与结论 |
|---|---|---|---|
| 机器人 | 可以 | 可以 | 优先使用 CC0 机器人 |
| 蜘蛛侠 | 不可以未经授权 | 可以 | 版权、商标和角色形象授权必须由用户确认 |
| 奥特曼 | 不可以未经授权 | 可以 | 版权、商标和角色形象授权必须由用户确认 |
| 免费真人比例角色 | 可以 | 可以 | 只使用 CC0 或明确允许分发的资产 |
| 动漫 VRM 角色 | 不默认内置 | 可以 | 加载器 MIT 不代表模型许可 |
| 用户自制角色 | 可以接入 | 可以 | 用户负责模型授权 |
| 原创英雄 | 可以 | 可以 | 不使用受保护角色的名字、标志和辨识性外观 |
| 机甲、机器人、外星人 | 可以 | 可以 | 重点检查骨骼和动作兼容性 |
| 吉祥物、动物舞者 | 可以 | 可以 | 需要重新定义手脚和尾巴动作 |
| 真人写实舞者 | 谨慎 | 可以 | 分发限制和体积较大，优先用户导入 |

### 1.1 IP 角色原则

- 项目不内置未经授权的蜘蛛侠、奥特曼和其他知名 IP 角色。
- 应用提供“用户导入角色槽”，用户可在本机导入已有模型。
- 导入时要求用户确认拥有使用权。
- 导入模型默认进入本地角色库，不进入云端，不进入比赛包。
- 动作包导出时默认只保存角色 ID 和兼容信息，不打包角色模型。
- 演示或比赛公开提交时，IP 角色需要单独准备授权证明。
- 可以内置原创英雄模板，但不能复制受保护角色的服装、标志和高度辨识性组合。

## 2. 角色分类体系

### 2.1 按模型类型

- 程序化角色：直接在代码中构建的基础几何体，稳定、最轻量、最低画质使用。
- GLB / GLTF 角色：主流骨骼动画模型，适合机器人和低模角色。
- VRM 角色：标准 Humanoid 虚拟人，适合动漫和真人比例角色。
- 用户导入角色：用户自己的模型，受本地许可证规则约束。
- 网络服务生成的虚拟人：不在首版运行时接入，避免隐私和网络依赖。

### 2.2 按舞蹈功能

- 标准舞者：左侧播放参考动作。
- 用户角色：右侧跟随摄像头实时动作。
- 教练角色：边角或舞台侧方，用于语音和提示。
- 幽灵角色：叠加显示参考轨迹或上次动作。
- 伴舞角色：仅在高端设备或特定模式下增加。
- 奖杯或装饰角色：结算页或大厅使用，不参与动作评分。

### 2.3 按视觉风格

- 工业机器人。
- 科幻机器人。
- 服务机器人。
- 机甲。
- 低模真人。
- 卡通舞者。
- 动漫 VRM。
- 原创英雄。
- 运动教练。
- 未来舞者。
- 吉祥物。
- 外星人。
- 骷髅或幻想角色。
- 全息/幽灵角色。

### 2.4 按性能等级

- 极低：双骨架、无贴图、无动画状态。
- 低：低模角色、单材质、无阴影。
- 中：机器人或低模真人、1K 贴图、简化阴影。
- 高：完整机器人、VRM、材质和基础表情。
- 超高：仅桌面演示使用，不是比赛默认。

## 4. 用户导入角色的产品流程

### 4.1 支持格式

首版支持：

- GLB。
- GLTF。
- VRM 0.x。
- VRM 1.0。

暂缓运行时直接支持：

- FBX。
- BLEND。
- PMX。
- 带外部脚本的模型。

FBX 可以在后续版本通过外部转换工具变成 GLB 后导入，避免把转换器和复杂依赖带进主运行时。

### 4.2 导入向导

步骤：

1. 选择模型文件。
2. 读取基础信息：名称、版本、作者、许可证、文件大小、贴图、动画、骨骼和渲染器。
3. 检查是否包含远程资源。
4. 检查是否包含脚本或不受支持的扩展。
5. 显示模型预览。
6. 自动识别骨骼。
7. 用户修正骨骼映射。
8. 进行 T-Pose / A-Pose 校准。
9. 测试标准动作。
10. 设置角色名称、分类、性别展示、体型、默认材质和性能等级。
11. 生成角色缩略图和全身预览。
12. 保存为本地角色。

### 4.3 导入结果

导入完成后生成：

- 角色 ID。
- 文件哈希。
- 缩略图。
- 全身预览图。
- 模型元数据。
- 骨架映射。
- 重定向配置。
- 许可证记录。
- 性能标签。
- 兼容的动作包类型。

### 4.4 导入失败状态

需要明确区分：

- 文件损坏。
- 不支持格式。
- 没有骨骼。
- 骨骼太少。
- 层级异常。
- 贴图缺失。
- 外部资源被阻止。
- 三角面太多。
- 显存不足。
- 许可证未确认。
- 模型包含不安全内容。

## 5. 统一 Humanoid 骨骼规范

### 5.1 必须骨骼

统一骨架至少包括：

- 根节点。
- 髋部。
- 脊柱。
- 胸部。
- 颈部。
- 头部。
- 左肩、右肩。
- 左上臂、右上臂。
- 左前臂、右前臂。
- 左手、右手。
- 左大腿、右大腿。
- 左小腿、右小腿。
- 左脚、右脚。

### 5.2 可选骨骼

- 手指。
- 脚趾。
- 上胸。
- 腰部。
- 眼睛。
- 下颌。
- 披风。
- 尾巴。
- 耳朵。
- 天线。
- 武器挂点。
- 粒子挂点。

### 5.3 骨骼能力标签

每个角色记录：

- `full_body`：完整身体。
- `hands`：支持手部骨骼。
- `fingers`：支持手指。
- `face`：支持面部表情。
- `root_motion`：支持根运动。
- `props`：支持配件挂点。
- `cloth`：支持布料或软体。
- `dual_hand`：双手动作稳定。
- `fast_rotation`：快速转身稳定。

动作包可以根据这些能力：

- 自动选择合适的角色。
- 禁用不支持的身体部位评分。
- 提示某些动作精度会下降。
- 自动回退到标准机器人。

### 5.4 最低兼容要求

正式跟舞角色至少要有：

- 髋、脊柱、头、双臂、双腿和双脚。
- 可用根节点。
- 明确初始姿态。
- 可读骨骼名称或手动映射能力。

只有上半身骨骼的模型只能进入“上半身训练模式”。

## 6. 核心重定向逻辑

### 6.1 总体数据流

```text
真人视频
  -> COCO-17 2D
  -> 3D Baseline 或高级后端
  -> 统一参考骨架
  -> 相对关节旋转
  -> 根节点和朝向
  -> Humanoid 标准姿态
  -> 目标角色骨骼映射
  -> 约束和平滑
  -> 3D 角色
```

### 6.2 不直接复制世界坐标

不同角色身高、骨骼长度和初始姿态不同，直接复制世界坐标会导致：

- 手穿过身体。
- 脚悬空。
- 头部倾斜。
- 关节爆炸。
- 体型比例扭曲。

正确策略：

- 算法输出统一骨架方向。
- 计算源骨架相对父关节的旋转。
- 将旋转转换为目标角色的局部旋转。
- 保留目标角色自身骨骼长度。
- 对根平移单独处理。
- 用约束防止反关节和穿模。

### 6.3 相对旋转

每个骨骼使用父骨和子骨的向量关系计算方向。

需要保存：

- 源骨架初始姿态。
- 目标骨架初始姿态。
- 源骨骼方向。
- 目标骨骼方向。
- 坐标轴转换。
- 左右和前后方向。
- 根节点缩放。

动作帧进入后：

- 计算源骨骼相对初始姿态的变化。
- 用四元数表示旋转。
- 把旋转转换到目标坐标系。
- 应用目标骨骼初始姿态。
- 对旋转进行插值和限幅。
- 再应用根平移、身体朝向和地面锁定。

### 6.4 根节点处理

根节点单独分为：

- 原地舞蹈模式：锁住水平位置，只保留旋转和上下起伏。
- 跟随移动模式：保留参考动作的平面位移。
- 安全模式：限制移动范围，避免角色跑出舞台。
- 镜像模式：对根节点左右方向做显式翻转。

默认建议：

- 训练模式使用原地或受限位移。
- 回放模式允许较大移动。
- 低端设备默认关闭根部大幅移动。

### 6.5 足部锁定

为了减少脚底滑动：

- 识别脚落地阶段。
- 对髋到膝、膝到脚使用两段 IK。
- 脚在地面附近且置信度足够时锁住脚底。
- 脚离地时恢复正向运动。
- 低置信度时不强行 IK，避免膝反折。

### 6.6 手部处理

- 普通舞蹈只映射手腕。
- 需要手指动作时，再映射手指。
- 模型没有手指时，忽略手指并降低相关评分权重。
- 抓取、OK 手势和道具动作单独标记为可选能力。
- VRM 的手指名称和机器人夹具名称通过映射表接入。

### 6.7 旋转约束

每种关节都有安全范围：

- 肩部：限制极限扭转。
- 肘部：限制反关节。
- 髋部：限制过度外旋。
- 膝部：只允许向后弯曲。
- 踝部：限制翻转。
- 脊柱：限制极端弯曲。
- 颈部：保护头部朝向。

约束不是把动作锁死，而是在异常帧避免角色飞出去。

### 6.8 平滑策略

- 单帧噪声使用动态滤波。
- 快速动作降低平滑，保留真实速度。
- 静止动作提高平滑，减少抖动。
- 遮挡帧冻结并预测有限时间。
- 重新置信后使用交叉淡化。
- 根节点使用低通滤波，避免画面晃动。

## 7. 角色动作状态机

每个角色不是只播放用户动作，还需要一组基础状态：

```text
NotLoaded
Loading
ReadyPose
Idle
Listen
Countdown
Dancing
Paused
Recovering
Success
Fail
Celebrate
Leaving
Unloaded
```

状态用途：

- Idle：站立待机，轻微呼吸或机械摆动。
- ReadyPose：准备姿势，和舞蹈包开始姿态接近。
- Countdown：3、2、1 倒计时姿态。
- Dancing：实时动作重定向。
- Paused：冻结动作，不允许评分。
- Recovering：摄像头恢复后重新定位。
- Success：完成动作、举手、发光或庆贺。
- Fail：动作失败时低强度反馈，不羞辱用户。
- Celebrate：结算或连击达成。
- Leaving：退出舞台动画。

状态切换：

- 使用动画混合。
- 不能从 Idle 硬切到 Dancing。
- 倒计时结束后切换到 Dancing。
- 暂停时冻结姿态和音乐。
- 结算时根据分数选择庆祝或鼓励状态。

## 12. 专业加载与缓存逻辑

### 12.1 资源生命周期

```text
发现资产
  -> 计算哈希
  -> 读取元数据
  -> 许可证校验
  -> 安全检查
  -> 加载模型
  -> 验证骨架
  -> 创建角色模板
  -> 生成实例
  -> 创建动画混合器
  -> 注册重定向配置
  -> 进入舞台
  -> 使用完成后释放
```

### 12.2 模板与实例

- 同一模型只加载一次模板。
- 左右角色如果需要同一个模型，使用骨架安全克隆。
- 每个角色实例有独立骨骼、材质覆盖和动画混合器。
- 材质尽量共享，变体只覆盖必要属性。
- 实例退出后释放动画、纹理和 GPU 资源。

### 12.3 缓存策略

- 当前角色：常驻。
- 下一个可能使用的角色：预加载元数据和缩略图，不预加载完整模型。
- 最近使用角色：保留有限缓存，LRU 淘汰。
- 低端设备最多缓存 1 个完整模型。
- 中端设备最多缓存 2 个。
- 高端设备最多缓存 3 至 4 个。
- 贴图和几何体单独计数，不能只按模型数量估算。

### 12.4 加载线程

主线程负责 UI 状态，后台线程负责：

- 文件哈希。
- 元数据解析。
- 图片缩略图。
- 许可证读取。
- 骨骼预分析。
- 大模型预检查。

WebGL 资源创建必须在 WebEngine 页面内执行，不能试图从 Python 直接创建 GPU 对象。

## 13. 代码模块建议

```text
src/dance_mirror/
  characters/
    registry.py          角色注册和索引
    models.py            角色、骨骼、能力和变体数据模型
    importer.py          导入和校验流程
    inspector.py         GLB/VRM 元数据和骨架检查
    library.py           角色库查询
    variants.py          颜色、材质、体型和配件
    licenses.py          IP 和资产许可证规则

  retarget/
    canonical.py         统一 Humanoid 骨架
    bone_map.py          骨骼名称映射
    rest_pose.py         初始姿态和校准
    solver.py            相对旋转和根节点求解
    constraints.py       关节约束和反关节保护
    foot_lock.py         足部锁定
    smoothing.py         四元数平滑和丢失恢复

  renderer/
    actors/
      actor_controller.py  单个角色生命周期
      actor_state.py       角色状态机
      actor_binding.py     骨骼和材质绑定
      lod.py               LOD 切换
      variants.py          视觉变体应用
    stages/
      reference_stage.py   左舞台
      user_stage.py        右舞台
      coach_stage.py       教练舞台
    cache/
      asset_cache.py       模型和纹理缓存
      resource_budget.py   显存和资源预算
```

### 13.1 模块职责

`characters`：

- 管理角色元数据。
- 不做动作计算。
- 不直接操作 Three.js。

`retarget`：

- 只处理骨架和旋转。
- 不依赖 PyQt6 页面。
- 可单独做单元测试。

`renderer.actors`：

- 负责加载、克隆、绑定和显示。
- 不负责视频解析和评分。

`stages`：

- 负责左右舞台隔离。
- 共享底层渲染器和缓存。
- 每个舞台有自己的相机和角色选择。

`cache`：

- 负责资源预算、缓存和释放。
- 不决定业务逻辑。

## 15. 性能预算

### 15.1 单角色预算

| 档位 | 三角面 | 贴图 | 骨骼 | 材质 |
|---|---:|---:|---:|---:|

| 中 | 8,000 至 25,000 | 1K | 30 至 60 | 2 至 4 |
| 高 | 25,000 至 50,000 | 2K | 60 至 120 | 4 至 8 |

### 15.2 双角色预算

- 平衡模式总三角面不超过 60,000。
- 高端模式总三角面不超过 120,000。
- 所有贴图默认按需加载。
- 同时使用透明材质不超过 4 个。
- 阴影只对主角色开启。
- 教练角色不参与阴影和物理。
- 装饰角色不加载骨骼动画。

### 15.3 低端回退顺序

1. 高模 VRM 切低模真人。
2. 低模真人切机器人。
3. 机器人切程序化角色。
4. 程序化角色切骨架。
5. 关闭教练和装饰角色。
6. 关闭材质变体和表情。
7. 降低动作更新频率。

## 16. 安全和许可证

### 16.1 模型文件

- 只允许受控格式。
- 禁止执行模型内脚本。
- 禁止远程 URI。

- 导出舞蹈包默认不包含角色模型。

- 比赛提交版本默认隐藏本地导入的 IP 角色，除非用户确认拥有授权。
- 应用内显示“仅本地使用”状态。

### 16.3 许可证

每个角色至少记录：

- 代码许可证。
- 模型许可证。
- 贴图许可证。
- 动画许可证。
- 声音和材质许可证。
- 角色 IP 许可证。
- 是否允许修改。
- 是否允许再分发。
- 是否允许商用。
- 是否需要署名。

## 20. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 模型没有标准骨骼 | 无法重定向 | 手动骨骼映射和兼容性检查 |
| VRM 模型许可混乱 | 无法发布 | 用户本地导入，不默认打包 |
| IP 角色版权风险 | 比赛或发布受影响 | 只支持本地槽位，不内置和导出 |
| 快速转身姿态爆炸 | 画面不可用 | 约束、平滑和置信度控制 |
| 手指动作不支持 | OK 手势无法由角色表现 | 手势只用于用户准备，角色手指可选 |
| 高低模切换闪屏 | 体验差 | 稳定窗口和淡入淡出 |
| 模型资源太大 | OOM | 大小、三角面、贴图和 LOD 限制 |
| 角色材质互相污染 | 换色影响其他实例 | 模板与实例分离，材质按需覆盖 |
| 缓存无法释放 | 越用越卡 | 引用计数、LRU 和显存预算 |
| 用户模型格式错误 | 应用崩溃 | 导入隔离、错误卡片和回退角色 |

## 21. 最终推荐

角色系统应按下面路线实施：

1. 先建立统一个人角色规范和角色库。
2. 接入可合法分发的机器人、低模真人、KayKit 和 Kenney 角色。
3. 完成 GLB、GLTF、VRM 本地导入向导。
4. 完成骨骼映射和动作重定向。
5. 接入角色变体、颜色、材质、配件和 LOD。
6. 支持左右舞台不同角色和教练角色。
7. 为用户导入的蜘蛛侠、奥特曼等 IP 模型提供本地槽位，但不随项目分发。
8. 最后做低端设备回退、缓存、释放和许可证审计。

这套方案可以让项目从“一个模型跟动作”升级为：

**一个舞蹈包，可以驱动机器人、真人比例角色、VRM、用户自制角色和原创英雄；同一个动作语义在不同角色上保持一致；低端设备自动降级；IP 角色合法本地导入；所有角色都能参与回放、训练、跟舞和结算。**

这才是真正可扩展、专业且不容易踩版权雷区的多角色 3D 舞蹈系统。
